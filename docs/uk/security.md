# Архітектура і модель безпеки

## Цілі

1. Ключ відкриває **лише** ті сайти й сервіси, які йому явно дали.
2. Жодного загального доступу до домашніх мереж, жодного доступу до роутерів, жодного трафіку між клієнтами.
3. Інтернет-трафік клієнтів ніколи не йде через VPS.
4. Удома нічого не відкрито в інтернет; на хабі відкрито лише SSH, WireGuard і (за бажання) публічні сайти через Cloudflare.
5. Втрата пароля панелі, телефона чи файлу копії не повинна віддати мережу.

## Рівні захисту

| Рівень | Як забезпечується |
|---|---|
| Конфіг клієнта | `AllowedIPs = 10.77.0.1/32`: пристрій спрямовує в тунель лише адресу хаба. |
| WireGuard на хабі | Кожен пір клієнта має `AllowedIPs = <його /32>`; підроблені адреси відкидає сам WireGuard. |
| Брандмауер хаба (nftables) | Вхідна політика `drop`; політика `forward` — `drop`: хаб нічого не маршрутизує між пірами чи в домашні мережі. Клієнтам доступні лише TCP 80/443 на хабі і дозволені їм порти TCP-сервісів. |
| Caddy | Кожен сайт має список дозволених VPN-адрес (`remote_ip`); інші ключі бачать сторінку «немає доступу». Панель відкривається лише адмін-ключам. На шляху через VPN заголовки `CF-Connecting-IP` і подібні прибираються, тож бекенд отримує їх лише від Cloudflare. |
| Роутер локації | Приймає з тунелю лише `src 10.77.0.1` на перелічені порти LAN; керування роутером із тунелю заборонено. |
| TCP-сервіси | `systemd-socket-proxyd` для кожного сервісу, `DynamicUser`, пісочниця, плюс правило nftables для кожного дозволеного ключа. |

Сам хаб звертається до домашніх сервісів лише через Caddy (сайти) або TCP-проксі (сервіси) і лише на адреси в мережах локацій чи адреси ключів. Власні порти керування хаба, loopback (крім вибраних портів для сайтів на VPS) і link-local/metadata-адреси як бекенд відхиляються.

## Вебпанель (vpnadmin)

- Працює від непривілейованого користувача `vpnadmin`, слухає `127.0.0.1:8090`; Caddy відкриває її лише адмін-ключам через тунель.
- Може запускати лише `sudo -n /usr/local/sbin/wgctl …` (sudoers), завжди з аргументами `--параметр=значення`, тож текст із форми ніколи не стане параметром.
- Вхід: пароль (scrypt) **і** TOTP; перевірки сталого часу; 5 невдач з адреси → блокування на 15 хвилин; код TOTP приймається лише один раз.
- Чутливі дії (завантажити конфіг, показати QR, дати права адміна, відкликати, опублікувати сайт, змінити отримувачів сповіщень) потребують **свіжого коду**; 5 невірних кодів завершують сесію.
- Сесії: cookie `__Host-` з HttpOnly, SameSite=Strict, 30 хвилин бездіяльності, не більше 10 сесій; зміна пароля завершує всі.
- CSRF-токен у кожній формі плюс перевірка Origin/Sec-Fetch-Site; сувора CSP (без вбудованих скриптів), HSTS, COOP/CORP, `frame-ancestors 'none'`.
- Довіряється лише останнє значення `X-Forwarded-For` і лише від Caddy на 127.0.0.1.
- Навіть повністю зламана панель лишається обмеженою: коли `wgctl` запущено через sudo від користувача `vpnadmin`, він приймає лише команди, які використовує панель. `init`, `backup restore/init/verify`, `tcp setup`, `location adopt`, `panel`, `cloudflare`, `render` і `geo update` працюють лише з SSH-терміналу.
- Після 20 невдалих входів з усіх адрес за 15 хвилин вхід закривається для всіх на 15 хвилин. До панелі доходять лише адмін-ключі, тож це здебільшого захист від викраденого ключа; якщо колись заблокує вас, зачекайте або перезапустіть `vpnadmin` через SSH.

## Моніторинг

`wgctl monitor` (щохвилини) позначає ключ, коли він з'являється з нової країни чи від хостинг/VPN-провайдера, через Tor, з неможливою швидкістю подорожі або з «подвійною активністю» (скопійований конфіг). Позначки ніколи не блокують автоматично; рішення за адміном (`trust` або `disable`). Геолокація — локальні бази DB-IP Lite, жодна IP не передається третім сторонам.

## Секрети на сервері

| Файл | Захист |
|---|---|
| `/etc/wireguard/wg0.conf`, `/etc/wgctl/` (конфіги клієнтів із приватними ключами) | лише root (600/700). Конфіги зберігаються, щоб загублений QR можна було показати знову; `wgctl reissue` змінює ключ. |
| `/etc/vpnadmin/auth.json` | користувач `vpnadmin`, 600; хеш scrypt, секрет TOTP, хеші резервних кодів. |
| `/etc/caddy/cloudflare.env` | root, 600; токен обмежений DNS однієї зони. |
| Резервні копії | зашифровані age на публічний ключ; секретного ключа на сервері немає. |

## Що ще варто зробити

- SSH лише за ключами (`PasswordAuthentication no`), бажано з кількох адрес.
- Увімкнені `unattended-upgrades`; перезавантаження, коли просить сторінка «Сервер».
- Секретний ключ копій і секрет TOTP — у менеджері паролів, не на VPS.
- Сайти давайте кожному ключу окремо; `*` (усі сайти) — лише для власних пристроїв.
- Після сповіщення «під підозрою» перегляньте журнал; якщо сумніваєтесь — **Заблокувати**, а не **Це я**.
